# v0.16.0 — SCM Governance: Branch Protection + Tag Immutability

Release date: 2026-05-15

Minor feature release under `docs/RELEASING.md`: this adds a new capability
surface (SCM-level governance enforcement via GitHub Rulesets) without
changing the scaffolded API, K8s identifiers, prediction schema, or any
existing template contract. v0.16.0 codifies what was previously an
aspirational claim in `docs/ADOPTION.md` (CC7.2 change management) into
an enforceable, reproducible artifact that adopters apply with one Make target.

## What's new

### Branch protection + tag immutability (ADR-026)

Two GitHub Repository Rulesets shipped as code:

- **`main-branch-baseline`** — protects `main` with: block force-push,
  block deletion, required PR, linear history, dismiss stale reviews on
  push, required conversation resolution, and exactly 6 required status
  checks drawn from the always-on PR set (Tests & Coverage Python 3.11
  + 3.12, Self-audit, Python Lint + Type Check, Agentic System
  Validation, Scaffolder End-to-End Test). Strict "up-to-date" off to
  avoid rebase churn at low PR volume. Bypass: `RepositoryRole: admin`
  only (break-glass, audit-logged). Required signed commits OFF — DCO
  already covers attribution.
- **`tag-immutability-v`** — locks `refs/tags/v*` against deletion and
  force-push to prevent release-on-tag hijack via tag recreation.

### New artifacts

- `docs/decisions/ADR-026-branch-protection.md` — full rationale, 6
  rejected options (1-approval, signed commits, strict-required,
  Golden Path as required, no bypass, per-environment duplication),
  revisit triggers, validation checklist.
- `docs/governance/branch-protection.md` — single source of truth
  for the exact configuration; the script and the ADR both reference it.
- `scripts/setup_branch_protection.sh` — idempotent `gh api` applier
  with `--dry-run`, `--check`, and the standard apply path. No hard
  `jq` dependency: picks `jq` → `python3 -m json.tool` → `cat` at
  startup. CI-ready: `--check` exits non-zero if either ruleset is
  missing or not active.

### New Make targets

```bash
make setup-github-preview   # show payloads, never mutates
make setup-github            # apply both rulesets (idempotent)
make setup-github-check      # verify both are active
```

### AGENTS.md operations matrix

Two new rows codifying the operation class:

- Apply branch-protection rulesets to a fresh fork → **CONSULT**
  (`make setup-github`; mutates repo SCM settings — never silent)
- Modify branch-protection rulesets on an existing repo → **STOP**
  (requires PR amending `docs/governance/branch-protection.md` +
  ADR-026 §Revisit triggers)

### Adopter surface

- `scripts/bootstrap.sh` Next Steps now surfaces SCM protection as
  step 4 between "validate agentic system" and "read the docs".
- `QUICK_START.md` gains a "Protect your fork" section explicit
  about CONSULT-class semantics.
- `README.md` Release-and-operate flow now references ADR-026 as
  the SCM baseline beneath the existing 9-step lifecycle.

## Why this matters

The previous template documented enterprise governance (`AGENTS.md`,
15 rules, 16 skills, 12 workflows, 32 anti-patterns, 24 ADRs) but did
not enforce it at the SCM layer. Without ADR-026, an actor with write
credentials could:

1. Force-push to `main` and erase commits that already passed CI.
2. Delete `main` and break the audit-baseline contract.
3. Delete and recreate a `v*` tag, re-executing `release-on-tag.yml`
   against arbitrary content (release hijack).
4. Bypass CI on a PR through admin override without leaving a
   reviewable audit trail.

None of those failure modes is detectable or preventable at the
agentic layer — they require rules on the Git server. v0.16.0
closes them with two rulesets and one Make target.

The single-maintainer reality (bus-factor=1) is honored throughout:
required approvals stay at 0 (forcing 1 with one CODEOWNER would
make every PR self-block); the revisit trigger is documented so the
choice flips the day a second CODEOWNER lands.

## Validation

- `scripts/setup_branch_protection.sh --dry-run` prints both JSON
  payloads with structure validated parseable.
- `make setup-github-check` returns 0 only when both rulesets exist
  with `enforcement=active` on the current `gh`-authenticated repo.
- All 4 always-on PR workflows (`validate-templates`, `ci-examples`,
  `pr-smoke-lane`, `pr-evidence-check`) confirmed running on every
  PR to `main` without `paths:` filters — the required-checks list
  is drawn from this set, so no phantom-required-check deadlock.
- `python3 scripts/verify_enterprise_adoption.py` updated to track
  the new release (constant bumped 0.14.0 → 0.15.3 with
  `RELEASE_DATE` constant for forward portability); still passes.
- Pre-commit hooks green (gitleaks, mypy, bandit, validate-agentic).

## What this release does NOT change

- No change to scaffolded service surface (`fastapi_app.py`,
  K8s manifests, Terraform, training/evaluation pipeline).
- No new dependencies (`gh` CLI was already in `bootstrap.sh`).
- No changes to existing CI workflows or required check names.
- No model artifact changes, no schema changes, no API changes.

This is purely a SCM governance addition. Adopters who do not
run `make setup-github` see exactly the v0.15.3 behavior — the
new capability is opt-in by design (CONSULT-class).

## Migration

No migration steps. Adopters on v0.15.3 update with:

```bash
git pull
make setup-github-preview   # review what would be applied
make setup-github            # apply to your fork (one-time)
```

## Posture

Designed-ready (L1+L2+L3). v0.16.0 strengthens L3 (governance
posture) without claiming L4 (real cloud cluster validation),
consistent with the position taken in ADR-024.
