# v0.15.3 - ML/Data Scientist Contract Hardening

Release date: 2026-05-15

Patch release under `docs/RELEASING.md`: this closes defects in
existing EDA and fairness contracts without changing the scaffolded
API surface, directory layout, Kubernetes identifiers, or public
prediction schema.

## What changed

- Training now treats `quality_gates.require_eda_artifacts=true` as a
  complete evidence contract. The run fails before tuning unless all
  canonical artifacts exist and load successfully:
  `eda_summary.json`, `schema_ranges.json`,
  `baseline_distributions.parquet`, `feature_catalog.yaml`, and
  `leakage_report.json`.
- The fairness gate now uses the same optimal decision threshold
  selected during evaluation. This prevents a model from passing
  fairness at `0.5` while serving at a different threshold.
- Fairness now writes `fairness.json` into the model output directory,
  evaluates the richer audit helper, fails closed when a configured
  protected attribute is absent, and blocks automatic quality-gate
  pass-through when DIR lands in ADR-021's `[0.80, 0.85)` consultation
  band.
- EDA source documentation now consistently names
  `baseline_distributions.parquet` and `feature_catalog.yaml` as the
  canonical artifacts. Legacy names remain transition outputs only.

## Why this matters

The previous template already documented the full EDA packet and the
ADR-021 fairness policy, but the training scaffold could still proceed
with only part of the packet and could evaluate fairness at a different
threshold from the one used by the model. That was a credibility gap
for the Machine Learning Engineer / Data Scientist function: the
template asked the role to own evidence, but did not make all evidence
load-bearing.

Recorded in `VALIDATION_LOG.md` Entry 010.

## Known limitations

- This release does not claim L4 production rollout evidence.
- The template still expects adopters to implement domain-specific
  feature transformations in `FeatureEngineer`; this release makes the
  EDA handoff stricter but does not auto-generate feature code.
- Fairness thresholds remain default policy; domain-specific stricter
  floors still require an adopter ADR addendum.

## Known follow-ons (scoped, not regressions)

- Generate service-specific `FeatureEngineer` skeletons from
  `feature_catalog.yaml` after a real adopter catalog is available as
  a fixture.
- Feed `fairness.json` directly into model-card generation so subgroup
  findings are copied into service documentation automatically.
